## 1. Executive Summary & Value Proposition

In an authentic martial arts MMORPG, player movement must feel responsive, visually smooth, and authoritative. Navigation across towns, forests, and dungeons must adhere strictly to physical terrain obstacles, preventing wall-hacking, speed-hacking, and position desynchronization.

This specification defines the authoritative movement, obstacle collision validation, anti-cheat checksum verification, deterministic 18-Hz frame progression, jump locomotion, and sit/stand meditation postures for JXServer. Incoming walk and run commands are checked against cryptographic session tokens. The simulation loop advances moving entities frame-by-frame along their trajectory vector, clamping movement at impassable terrain obstacles. Sitting characters enter a resting posture that accelerates health and mana regeneration, while any subsequent movement immediately breaks the sitting state.

## 2. User Scenarios & Acceptance Criteria *(mandatory)*

### User Story 1 — Obstacle-Validated Walk and Run Progression (Priority: P1)

A player or autonomous bot commands their character to walk or run toward target coordinates on the map. The server validates the action, immediately broadcasts the movement trajectory to observers in the 3x3 region neighborhood, and advances the character's position deterministically across 18-Hz simulation frames at their designated speed. If the trajectory intersects impassable map obstacles, the server authoritatively halts the character at the last walkable coordinate and synchronizes their final position.

**Why this priority**: Walking and running are the core means of navigation and world exploration. Authoritative obstacle validation is vital to prevent wall-hacking and terrain exploits.

**Independent Test**: Connect a character to an active map. Issue walk and run commands toward walkable coordinates, observing continuous progression. Then command the character to move through a full-obstacle barrier (such as a town wall or mountain). Verify that the character stops precisely at the obstacle perimeter and returns to a standing posture without clipping.

**Acceptance Scenarios**:
1. **Given** a standing character on a walkable cell, **When** the client submits a valid walk or run command toward an unobstructed destination, **Then** the server broadcasts the trajectory to observers in the 3x3 region neighborhood, advances the character's coordinates each 18-Hz frame at their movement speed (10 Mps/tick for walking, 20 Mps/tick for running), and transitions to standing posture upon arrival.
2. **Given** a character walking or running toward an obstacle cluster, **When** the character's trajectory reaches an impassable cell (`Obstacle_Full`), **Then** the server halts the character at the last passable coordinate, halts progression, transitions to standing posture, and broadcasts an authoritative position synchronization.
3. **Given** a moving character crossing from one spatial region into another, **When** the character's coordinates cross the region boundary, **Then** the server automatically updates the character's spatial region membership, triggering 3x3 AOI visibility adjustments.

### User Story 2 — Anti-Cheat Security Verification for Movement Commands (Priority: P1)

To prevent tampered or unauthorized movement packets generated by third-party speed-hacks or packet injectors, the server validates the security checksum included in every walk and run command against the player's secret session tokens negotiated during world entry. Commands failing verification are dropped, preserving the character's authoritative position.

**Why this priority**: Preserving game integrity requires rejecting unauthorized or spoofed movement requests before they can alter world state.

**Independent Test**: Connect a simulated client. Send walk and run packets with correct checksums, verifying normal movement. Then send a packet with an altered or zero checksum; verify that the server rejects the command, logs a security warning, and leaves the character stationary.

**Acceptance Scenarios**:
1. **Given** an active authenticated session with recorded world-entry tokens, **When** a walk or run command arrives with a checksum satisfying the canonical key formula (`(dwCheckValue ^ token1 ^ token2) % key == 0`), **Then** the server accepts the command and initiates movement progression.
2. **Given** an active session, **When** a walk or run command arrives with a zero checksum or an invalid checksum value, **Then** the server discards the command, records a security diagnostic, and preserves the character's current coordinates.

### User Story 3 — Posture Transitions: Sitting Meditation & Jumping (Priority: P2)

Players can toggle their posture to sit (meditate) or perform a physical jump. While seated, the character remains stationary and enjoys accelerated health and mana recovery over time. Initiating a walk, run, jump, or manual stand command instantly breaks the sitting posture.

**Why this priority**: Sitting is essential for players to regenerate vitals between combat encounters, while jumping enables tactical repositioning across short distances.

**Independent Test**: Place a damaged character into sitting posture. Measure the periodic health and mana regeneration over several seconds to confirm accelerated recovery. Command the character to move or jump, verifying immediate posture transition and broadcast.

**Acceptance Scenarios**:
1. **Given** an active character in standing posture, **When** the client submits a sit toggle command, **Then** the server transitions the character to sitting posture, broadcasts the posture update to the 3x3 neighborhood, and accelerates periodic health and mana regeneration each second.
2. **Given** a seated character, **When** the client submits a walk, run, or jump command, **Then** the server immediately cancels the sitting posture, transitions the character to the active movement posture, and resumes normal vital regeneration rates.
3. **Given** a character standing on a walkable cell, **When** the client submits a jump command to a valid nearby coordinate, **Then** the server broadcasts the jump trajectory to the 3x3 neighborhood and updates the character's position upon completion.

## 3. Edge Cases & Boundary Conditions

1. **Simultaneous Destination Arrival and Obstacle Encounter**: The final destination cell itself is blocked; the server halts at the preceding passable cell without overshooting.
2. **High-Frequency Checksum Rotation**: Autonomous clients submitting multiple walk/run commands per second maintain consistent token state without desynchronization.
3. **Movement Interruptions during Sit Regen Tick**: A movement command arrives on the exact simulation frame where sitting regeneration executes; regeneration is calculated for the elapsed frames, and posture is cleanly switched to walking/running.
4. **Zero-Distance Movement**: A client sends a walk or run command targeting the character's exact current coordinates; the server transitions directly to standing without dividing by zero in direction math.
5. **Jump across Unwalkable Gaps**: Jumping over low terrain obstacles lands authoritatively only on valid walkable destinations.

## 4. Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The engine MUST validate the 4-byte security checksum (`dwCheckValue`) on incoming walk (key `0x24A1`) and run (key `0x1D78`) packets against the session's recorded synchronization tokens (`token1`, `token2`), dropping commands where `dwCheckValue == 0` or `((dwCheckValue ^ token1 ^ token2) % key) != 0`.
- **FR-002**: When a valid walk command is received, the engine MUST immediately broadcast `s2c_npcwalk` (`0x50`, packing `NpcID, DestMpsY, DestMpsX`) to all players in the 3x3 region neighborhood.
- **FR-003**: When a valid run command is received, the engine MUST immediately broadcast `s2c_npcrun` (`0x51`, packing `DestMpsY, NpcID, DestMpsX`) to all players in the 3x3 region neighborhood, preserving the historical asymmetric wire layout.
- **FR-004**: During each 18-Hz simulation tick (Phase 500), the movement system MUST advance walking characters at their `WalkSpeed` (default 10 Mps/tick) and running characters at their `RunSpeed` (default 20 Mps/tick) along the normalized direction vector toward their destination.
- **FR-005**: Prior to advancing coordinates each frame, the engine MUST verify that the target cell in the map's obstacle grid does not have full impassability (`Obstacle_Full == 1`); if an obstacle is encountered, progression MUST stop at the last passable coordinate and transition the entity to standing posture (`do_stand`).
- **FR-006**: When an entity crosses a region boundary during frame progression, the engine MUST update the entity's spatial region grid registration and recalculate 3x3 AOI visibility.
- **FR-007**: The system MUST process jump commands (`c2s_npcjump` `0x4E` -> `s2c_npcjump` `0x54`), updating coordinates and broadcasting the jump action.
- **FR-008**: The system MUST process sit/stand posture commands (`c2s_npcsit` `0x71` -> `s2c_npcsit` `0x53`), transitioning entity posture, accelerating health and mana regeneration while seated, and automatically canceling sitting posture upon initiating movement.

---

### Key Entities

- **MovementCommandHandler**: Dedicated modular command handler processing walk, run, jump, and posture requests from player sessions.
- **MovementAndPostureZoneTickSystem**: Phased 18-Hz tick system (Phase 500) responsible for stepping positions along movement vectors, evaluating obstacle collisions, updating region boundaries, and ticking sitting vital recovery.
- **RegionObstacleGrid**: Fast binary bitmask representing passable, full-obstacle, and water cells across a 16x32 cell region.
- **MovementAntiCheatConsts**: Canonical verification keys and checksum validation algorithms matching client packet formatting.

## 5. Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 100% of movement commands with invalid or tampered security checksums are rejected, leaving the character's authoritative position unchanged.
- **SC-002**: Characters walking or running toward map obstacles halt cleanly at the obstacle perimeter with 0% wall-clipping across 1,000 automated path steps.
- **SC-003**: In-memory simulation stepping advances walking characters at exactly 10 Mps/tick and running characters at exactly 20 Mps/tick with sub-millimeter mathematical precision.
- **SC-004**: Sitting characters achieve their accelerated vital regeneration rate on their scheduled 1-second intervals, and 100% of movement commands instantly interrupt sitting posture.
